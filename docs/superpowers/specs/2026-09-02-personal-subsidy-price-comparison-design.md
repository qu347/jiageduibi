# 个人国补比价工具设计规格

状态：已在对话中确认，等待书面规格复核  
日期：2026-09-02  
项目目录：`D:\商品信息获取`

## 1. 产品目标

本项目是在 Windows 本机运行的个人商品比价工具。第一版聚焦手机品类，先支持 iPhone 17 系列标准型号，并通过京东、天猫/淘宝、拼多多三类平台报价演示完整流程。

用户输入“苹果17”后，系统先要求选择准确型号与规格，再接收浏览器扩展、本地测试夹具或手动录入的候选商品。系统排除配件、错误型号、错误容量、非全新、合约机、分期月供和以旧换新宣传价等干扰项，计算真正可比较的普通购买价格，区分已确认国补、预计国补和未知状态，最后按可比较价格排序。

软件只整理公开展示且由用户主动提交的信息，不代替平台认定补贴资格，也不自动登录、领券、加购或下单。所有涉及国补的页面持续显示“实际资格与成交价以平台结算页为准”。

## 2. 第一版范围

### 2.1 纳入范围

- Windows 本地运行，单用户、单机 SQLite 数据库。
- 手机品类和可扩展的通用型号词典。
- iPhone 17、iPhone 17 Pro、iPhone 17 Pro Max 等首批演示型号；具体规格数据在实现时以可核验来源为准，不把示例当作实时官方信息。
- 京东、天猫/淘宝、拼多多三个隔离的平台适配器。
- 固定夹具、手动录入、粘贴商品链接和浏览器扩展采集当前页。
- 单页工作台、历史价格、型号词典、国补规则和设置管理。
- 全国省市选择；普通比价不要求地区，国补估算前必须选择省市。
- PowerShell 一键开发、测试、构建和启动脚本。
- 固定数据端到端验收，以及逐个平台执行的真实页面人工验收。

### 2.2 不纳入范围

- 多用户、注册、登录、云同步、会员、支付和订单系统。
- 自动获取国补资格、保存身份材料或保证补贴可用。
- 自动领取优惠、加购、下单或支付。
- 保存账号密码、Cookie、身份证、银行卡、地址、订单或支付信息。
- 绕过登录、验证码、接口签名、频率限制或平台风控。
- 破解 App 私有接口、无人值守高频采集或批量扫描。
- 核心功能稳定前投入 Tauri 安装包、美化安装程序或代码签名。

## 3. 方案选择

采用“本地 Web 应用 + Manifest V3 浏览器扩展 + SQLite”的方案。

立即引入 Tauri 会增加 Rust 环境、Python sidecar、进程管理和安装包调试成本；扩展独立方案又无法清晰承载型号词典、全国规则、历史趋势和备份恢复。因此第一版先提供本地 Web 形态，生产启动时由 FastAPI 提供编译后的前端文件并自动打开默认浏览器。核心稳定后再单独评估 Tauri。

## 4. 系统架构

### 4.1 技术栈

- 后端：Python 3.12、FastAPI、Pydantic 2、SQLAlchemy 2、Alembic、SQLite、RapidFuzz、httpx、pytest。
- 前端：Vue 3、TypeScript、Vite、Pinia、Vue Router、Element Plus、Vitest。
- 扩展：Chrome/Edge Manifest V3、TypeScript、Vite、Vitest 和本地 HTML/JSON 测试夹具。
- 端到端：Playwright，优先使用本机 Microsoft Edge。
- 包管理：后端使用项目内 `.venv` 和 `pyproject.toml`；前端与扩展使用 pnpm 和锁文件。依赖版本在实施计划开始时根据当前稳定兼容版本锁定，不修改全局 Python 或 Node.js。

### 4.2 运行组件

1. `backend` 监听 `127.0.0.1`，提供 API、业务规则、数据库和生产前端静态文件。
2. `frontend` 在开发模式下由 Vite 单独运行，在生产构建后由后端提供。
3. `extension` 只在用户点击“采集当前页”时读取受支持平台的当前商品页面，并提交结构化报价。
4. `data` 保存 SQLite 数据库、可导入目录和用户主动生成的备份；运行数据不进入 Git。
5. `fixtures` 保存脱敏、固定且可复现的测试页面或 JSON，不用真实网络响应冒充稳定支持。

## 5. 核心数据流

```text
关键词
  → 本地型号词典搜索
  → 用户确认标准型号和规格
  → 创建唯一标准 SKU 与搜索会话
  → 生成平台搜索链接
  → 扩展采集 / 固定夹具 / 手动录入
  → 平台适配器标准化
  → 去重与字段提取
  → 干扰项排除与 SKU 匹配
  → 普通价、条件价和国补状态计算
  → 排序与结果解释
  → 保存当前报价和历史快照
```

输入关键词只查询本地型号词典，不直接混合展示平台搜索结果。只有用户确认型号、容量、版本、成色和颜色选择后，系统才创建搜索会话并接收报价。

每个平台适配器只负责识别自己的页面、提取原始字段和转换统一结构。匹配、价格和国补逻辑全部位于共享后端服务，避免三个适配器各自实现不同规则。

## 6. 标准型号词典

型号层级为品牌、产品系列、标准型号和标准变体。标准变体至少包含：

- 品牌、系列、型号名、型号代码、品类。
- 容量、内存、颜色、地区版本、成色。
- 别名和启用状态。

关键词检索先做规范化和别名完全匹配，再使用 RapidFuzz 做候选排序。模糊匹配只用于推荐标准型号，不会直接确认 SKU。

型号词典支持管理页面编辑和 JSON 导入导出。数据结构不包含苹果专用分支，新增华为、小米、荣耀、OPPO 或 vivo 时不修改核心匹配代码。

## 7. 统一报价与匹配

### 7.1 统一报价

统一报价包含平台标识、平台商品与 SKU 标识、标题、链接、店铺、解析后的商品属性、价格组成、国补状态、库存、匹配信息、地区、来源、采集时间和适配器版本。

所有金额保存为整数分。输入解析时拒绝无法明确识别币种或总价的值，不使用二进制浮点数参与金额计算。

### 7.2 去重

搜索会话内按“平台 + 平台商品 ID + 平台 SKU ID”去重。缺少稳定 SKU ID 时，使用规范化链接、店铺和标题指纹作为降级键，并在结果中标记降级去重。

刷新报价不会覆盖历史快照。当前报价更新和新快照写入位于同一数据库事务中。

### 7.3 匹配顺序

1. 识别配件、服务、定金、月供、回收抵扣、二手、翻新、展示机、官换机、合约机等排除信号。
2. 提取品牌、型号、容量、版本、成色、颜色和套装信息。
3. 校验必须匹配的品牌、型号、容量、版本和成色。
4. 按用户选择处理颜色、店铺类型和套装类型。
5. 计算匹配分数并记录每一项加减分原因和规则版本。

型号解析使用最长且最具体的型号优先规则，避免把 Pro Max 识别为 Pro 或普通版。容量使用边界明确的单位解析，避免将 512GB 混入 256GB。第一版默认只比较全新商品。

匹配阈值：

- 95–100：关键字段完整且完全匹配，进入默认结果。
- 85–94：关键字段匹配但非核心字段缺失，进入结果并标记“建议核验”。
- 70–84：进入待审核列表，不参与默认排名。
- 低于 70：排除。

## 8. 价格与排序规则

普通优惠后价格只减去已明确适用于当前商品的商家优惠和平台券。已确认国补只有在页面明确显示当前 SKU、地区和店铺可用时才计入默认可比较价格。

预计国补单独生成 `estimated_final_price`，用于展示估算，不参与默认普通购买价排序。会员、指定支付、拼团、直播间、以旧换新和其他条件价格也单独展示，默认不参与排序。

默认排序键依次为：

1. 是否存在可靠的可比较总价。
2. 可比较价格升序。
3. 平台自营、官方旗舰店、品牌授权店、第三方店铺的优先级。
4. 采集时间倒序。
5. 稳定的报价 ID，保证重复排序结果一致。

颜色选择“不限”时允许比较所有颜色，但必须显示最低价对应颜色。相同 SKU 不同颜色存在差价时，结果显示价格区间。

## 9. 全国国补规则

国补规则不硬编码在页面或匹配逻辑中。规则至少包含地区代码、品类、有效期、单价限制、补贴比例、补贴上限、能效要求、数量限制、参与平台、参与店铺类型、说明、来源链接、核验时间和启用状态。

普通价格比较不要求用户选择地区。用户希望查看国补时必须选择省、市；没有足够地区信息时返回 `unknown`。

规则匹配优先级为：

1. 市级规则优先于省级规则，省级规则优先于全国通用说明。
2. 必须处于有效日期范围并匹配品类、平台和店铺类型。
3. 同级规则冲突时，优先使用已核验且核验时间较新的规则。
4. 仍有冲突或字段不足时返回 `unknown`，不猜测补贴。

国补状态只允许：

- `confirmed`：平台页面明确确认当前 SKU、地区和店铺可用。
- `estimated`：本地规则推算可能符合，但平台未确认。
- `not_eligible`：规则明确判定不符合。
- `unknown`：信息不足或规则冲突。

初始规则库可以提供结构演示，但不得把未经当前来源核验的金额标记为真实有效规则。

## 10. 单页工作台界面

用户已选择“单页工作台”而非分步向导。页面同时展示搜索、筛选和结果，但保留“确认标准 SKU”的业务门槛，防止不同型号或容量进入同一排序。

### 10.1 主工作台

- 顶部：关键词、地区、搜索和手动刷新。
- 左侧：标准型号、容量、版本、成色、颜色、店铺类型、条件价和以旧换新开关。
- 右侧：标准 SKU 摘要、有效与排除数量、排序模式、平台筛选和报价表格。
- 报价行：平台、标题、型号规格、颜色、店铺、普通活动价、优惠、国补状态、可比较价、库存、更新时间、匹配置信度和原平台链接。
- 展开行：价格组成、条件说明、匹配原因、数据来源、适配器版本和排除警告。

### 10.2 其他页面

- 历史价格：按标准 SKU 查看各平台曲线、近期最低价、历史最低价和来源。
- 型号词典：编辑、启停和 JSON 导入导出。
- 国补规则：按省市、日期和状态筛选、编辑及导入导出。
- 设置：扩展连接、平台健康、默认筛选、备份恢复和历史清理。

## 11. 浏览器扩展与本地安全

扩展使用 Manifest V3，只申请实现功能所需的最小权限。采集只在用户点击“采集当前页”时发生，不扫描浏览历史，不读取密码输入框、Cookie、聊天、订单、地址或其他无关数据。

扩展首次连接时，用户从软件设置页复制一次性配对码到扩展。后端交换并保存本机扩展令牌；令牌存入扩展本地存储，报价写入接口必须携带令牌。令牌可以在软件设置页撤销和重新配对。

后端仅监听 `127.0.0.1`，CORS 只允许开发前端和已配对扩展所需来源。公开健康检查与只读状态接口不接受敏感输入，报价提交和管理写操作要求本地令牌。

遇到登录或验证码时，扩展停止采集并提示用户手动处理。扩展不尝试绕过限制，也不静默返回伪造空结果。

## 12. 平台适配器

每个平台适配器实现：搜索链接生成、URL 识别、搜索页解析、商品页解析、统一标准化、字段校验和健康检查。

京东、淘宝/天猫和拼多多适配器完全隔离。一个平台页面变化只影响该平台状态。适配器返回结构化错误，不把缺失字段猜成价格。

第一阶段以本地固定夹具验证解析契约。之后按京东、淘宝/天猫、拼多多顺序进行真实页面人工验收。真实验收由用户在 Edge 中自行登录和处理验证码；软件不接触账号凭证。若桌面页面无法稳定提供某些字段，文档必须记录限制，并保留粘贴链接和手动录入兜底。

## 13. API 边界

第一版 API 分组如下：

- 健康与平台状态：`/api/health`、`/api/platforms/status`。
- 型号词典：搜索、详情、JSON 导入和导出。
- 搜索会话：创建、读取、接收报价和完成会话。
- 报价：列表、详情、手动录入和待审核结果。
- 历史：按标准 SKU、平台和时间范围查询。
- 国补规则：查询、新增、更新、启停、导入和导出。
- 本地管理：扩展配对、备份、恢复和历史清理。

请求与响应使用明确的 Pydantic Schema。数据库写入使用事务，错误响应使用统一结构，OpenAPI 文档由 FastAPI 自动生成。

## 14. 数据库设计

核心表：

- 型号词典：`brands`、`product_series`、`product_models`、`product_variants`、`product_aliases`。
- 平台与店铺：`platforms`、`shops`、`platform_products`。
- 搜索与报价：`search_sessions`、`offers`、`price_components`、`price_snapshots`。
- 匹配与纠正：`offer_matches`、`manual_corrections`。
- 国补与运行状态：`subsidy_rules`、`adapter_runs`、`app_settings`、`backups`。

型号、规则和当前报价采用软删除，以便保留历史引用。用户主动执行历史清理时才物理删除符合条件的快照。适配器运行记录可按保留策略物理清理。删除和恢复操作都记录时间，不记录个人身份信息。

## 15. 备份与恢复

备份前提交数据库事务并执行 SQLite 检查点，然后复制数据库及必要的应用版本元数据。备份文件默认位于用户选择的本地目录，不自动上传。

恢复时先复制到临时位置，校验 SQLite 完整性、迁移版本和必要表结构，再关闭当前数据库连接并原子替换。任何校验或替换失败都保留原数据库，并返回可操作的错误说明。

## 16. 异常处理

统一错误结构至少包含：错误代码、发生的事情、可能原因、部分结果是否保存、用户下一步操作和可选技术摘要。

必须覆盖：

- 后端未启动或扩展未连接。
- 平台要求登录或出现验证码。
- 页面结构变化、适配器版本不兼容或价格字段缺失。
- 搜索无结果、全部被排除或只有待审核结果。
- 页面只展示月供、定金或回收抵扣宣传价。
- 国补状态无法确认或本地规则过期。
- 商品链接失效、数据库迁移失败、数据库损坏或备份恢复失败。

单个平台失败时，其他平台结果继续显示。系统明确说明本次是否保存了部分结果，不用“未知错误”或“请求失败”作为唯一提示。

## 17. 测试策略

### 17.1 后端

pytest 按 TDD 覆盖关键词映射、型号与规格匹配、配件和服务排除、Pro 系列边界、容量边界、二手与翻新、月供与回收价、普通价、确认与预计国补、稳定排序、去重、SQLite 持久化、Alembic 升降级和 API 错误。

### 17.2 前端

Vitest 覆盖“苹果17”型号建议、标准 SKU 确认、筛选、搜索会话、结果排序、国补标签、条件价隔离、空状态、解析失败和历史展示。

### 17.3 扩展

Vitest 和本地夹具覆盖域名识别、三平台解析契约、非商品页、配件、缺失价格、登录与验证码状态，以及不读取密码、Cookie 和无关页面字段的边界。

### 17.4 端到端

Playwright 使用固定数据完成：搜索“苹果17”、选择 iPhone 17 256GB 国行全新、导入三平台报价、排除五类干扰项、区分确认与预计国补、按可比较价格排序、打开测试链接、生成历史快照并验证重启后持久化。

真实平台采集是独立人工验收。固定夹具通过不等于真实平台已经稳定支持。

## 18. 实施阶段

1. 项目骨架与数据库：Git、目录、健康检查、Vue 外壳、Alembic 首迁移和统一测试脚本。
2. 型号词典：表结构、iPhone 17 系列可核验种子、关键词搜索、标准 SKU 选择和导入导出。
3. 报价核心：统一报价、匹配排除、价格与国补状态、去重、排序和历史快照。
4. 单页工作台：筛选、结果、详情展开、历史和设置页面。
5. 扩展通信：Manifest V3、配对、采集当前页和连接状态。
6. 平台夹具：京东、淘宝/天猫、拼多多解析器及健康状态。
7. 真实页面适配：按平台独立人工验收并记录限制。
8. 本地交付：备份恢复、文档、一键启动、完整回归和 Tauri 可行性复评。

每个实现阶段先写失败测试，再写最小实现。阶段结束必须运行对应验证命令，并按“完成项、主要文件、测试结果、真实验收、已知限制、Git 状态和下一阶段”格式汇报。

## 19. 成功标准

最小可用闭环达到：

- 输入“苹果17”后先选择标准型号和规格。
- 固定数据完整演示三平台同款比价。
- 正确排除配件、不同型号、不同容量、二手、月供和回收宣传价。
- 普通价、条件价、确认国补、预计国补和未知状态清楚区分。
- 默认按可靠的可比较价格升序排列。
- Edge 可加载扩展骨架并与本地服务配对。
- 点击报价能打开原平台或测试链接。
- 刷新保存历史快照，重启后数据仍存在。
- 后端、前端、扩展和固定数据端到端测试通过。

完整第一版还要求至少一个平台完成真实页面人工采集验收；其他平台若受页面限制，必须明确标记未验证或部分支持，并保留手动录入兜底。

## 20. 已知风险

- 平台页面结构、登录要求和反自动化策略会变化；适配器必须允许单独失效和快速更新。
- 拼多多等平台桌面网页可能缺少完整 SKU 或国补字段；真实能力只能在人工验收后确认。
- 国补规则具有地区、日期、额度和店铺参与差异；本地估算不能替代结算页。
- iPhone 17 系列及后续型号数据必须使用可核验来源更新，不能长期依赖演示别名。
- Node.js 24 较新，个别前端工具若存在兼容问题，应优先锁定兼容版本或使用项目级运行时方案，不擅自修改全局 Node.js。
- 当前未安装 Rust，因此 Tauri 不属于首轮交付阻塞项。
